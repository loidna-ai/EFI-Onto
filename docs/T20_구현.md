## 구현 (TTL 48.6 절)

- 분류표는 `efi_classification.ttl` 의 SKOS 개념이다(`kfc:Factor-Electrical-01` … `-10`, `skos:notation` 이 코드,
  `skos:definition` 이 매뉴얼 정의, `dcterms:source` 가 쪽수). 접두어가 다르므로 가설 라벨과 겹쳐도 lint 가 잡지 않는다 —
  공식 체계의 이름은 우리가 정의한 것이 아니기 때문이다. 처음에는 efi: 개체(`ReportCauseCategory`)로 만들었다가
  지식 그래프 기준으로 SKOS 로 옮겼다(2026-09-04, 브랜치 kg/classification).
- `reportedAs` — 가설 클래스 → 개념. 여덟 줄. '정확히 같다'일 때만 쓴다.
- **D-20** `ReportClassificationDerivationRuleShape` (sh:order 7): `Conclusion → concludes → 가설 클래스 → reportedAs` 이면
  `<결론>_classification` 개체를 만든다 — `FireCauseClassification`, `classifiesCause`, `usesClassificationSystem`,
  `hasReportCategory`, `classificationCategory`(원문 라벨). C-9·C-10 이 검증한다.
- **C-62** `ReportCategoryBelongsToSystemShape`: `hasReportCategory` 의 개념이 속한 개념 체계(`skos:inScheme`)가
  `usesClassificationSystem` 의 체계에 `dcterms:isPartOf` 로 속해야 한다(§19.8.1). 다른 체계의 항목을 빌리면 라벨만 같고 뜻이 다르다. D-20 의 산출을 읽는 규칙이기도 하다.
- SPARQL 접두어에 `skos` 를 더했다(선언 블록). Python 쪽은 손대지 않았다 — 결론 제약을 두 번 적지 않는다.

## 판단 경계

- 분류 개체가 있어도 결론의 확신도·점수는 바뀌지 않는다. D-20 은 결론을 읽기만 한다.
- 판단보류는 분류 개체가 없다. '미확인 단락'은 §19.6.5.1 원인미상 안의 이름이지 결론이 아니다.
- 2025년 훈령 이후의 NFDS 소분류 코드표를 받으면 2019년 매뉴얼과의 차이를 확인한다. '이물 혼입'의 자리도 그때 본다.
- 매뉴얼은 발화열원 26종을 발화요인과 별개 축으로 둔다. 이 온톨로지에 그 축은 없다 — 넣지 않는다. 발화열원(전기적 아크 등)은
  가설의 메커니즘 축이 이미 맡고 있고, 보고서 칸을 위해 축을 하나 더 만들면 판정과 무관한 기록이 자란다.
